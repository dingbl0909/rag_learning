# `ctrip_assistant` 项目代码解析

这份文档用于梳理 `ctrip_assistant` 项目中和 `LangChain`、`LangGraph`、`Agent`、`Tool Calling`、`状态管理`、`多 Agent 切换` 相关的核心代码，方便后续按文件逐步学习。

---

## 1. 项目本质

这个项目本质上是一个基于 `LangChain + LangGraph` 构建的多 Agent 工作流系统。

它不是传统意义上“一个 Prompt + 一个大模型 + 一个接口”的简单问答程序，而是分成了四层：

1. `LLM 层`  
   初始化模型、绑定工具、构建 runnable。

2. `Agent 层`  
   定义主 Agent 和多个子 Agent，各自负责不同领域任务。

3. `Graph 层`  
   用 LangGraph 管理状态、节点、路由、Agent 切换、中断和恢复。

4. `API 层`  
   把 graph 封装成 HTTP 接口，供前端或外部服务调用。

如果只用一句话概括：

`LangChain` 负责定义“每个 Agent 如何思考与调工具”，`LangGraph` 负责定义“多个 Agent 如何切换与共享状态”。

---

## 2. 项目整体执行链路

项目主执行流程如下：

1. 用户通过接口提交问题。
2. `api/graph_api/graph_views.py` 调用 `graph.stream(...)`。
3. `graph_chat/finally_graph.py` 中编译好的总图开始执行。
4. 固定先进入 `fetch_user_info` 节点。
5. 根据 `dialog_state` 判断：
   - 没有子流程状态时进入 `primary_assistant`
   - 有状态时恢复到当前子 Agent
6. 主 Agent 分析当前问题。
7. 如果需要分发任务，主 Agent 输出一个“委托工具”的 `tool_call`。
8. 图根据 `tool_call` 路由到某个子 Agent。
9. 子 Agent 使用自己的 prompt 和工具继续处理任务。
10. 如果涉及敏感工具，会在执行前被 `interrupt_before` 中断。
11. 用户确认后，从断点继续执行。
12. 子 Agent 完成后，通过 `CompleteOrEscalate` 或 `leave_skill` 回到主 Agent。
13. 图返回最终回复。

你可以把它理解成：

`HTTP 请求 -> graph.stream() -> fetch_user_info -> primary_assistant -> 子 Agent -> tool 节点 -> 回子 Agent / 回主 Agent -> 返回结果`

## 5. 主 Agent 的定义方式

### 文件

`graph_chat/assistant.py`

这个文件里有两个最核心的点。

### 5.1 `CtripAssistant`：把 runnable 包装成 Graph 节点

```python
class CtripAssistant:
    def __init__(self, runnable: Runnable):
        self.runnable = runnable

    def __call__(self, state: State, config: RunnableConfig):
        while True:
            result = self.runnable.invoke(state)
            ...
        return {'messages': result}
```

### 它的职责

- 接收一个 `LangChain runnable`
- 在 LangGraph 里作为节点执行
- 输入是 `state`
- 输出是 `{"messages": result}`

### 为什么要这么封装

因为 LangGraph 的节点通常要接收状态并返回状态增量，而 LangChain 的 runnable 只负责“基于 prompt 和 tools 调模型”。  
这个类就是两者之间的桥梁。

它内部还有一个小的工程化补丁：

- 如果模型没有产出有效内容
- 就自动补一条提示，要求它重新给出真实输出

所以它本质上是：

**把 LangChain runnable 封装成 LangGraph node 的适配器。**

---

### 5.2 主 Agent 的 runnable

主 Agent 的构造方式很典型：

```python
primary_assistant_prompt = ChatPromptTemplate.from_messages(...)
assistant_runnable = primary_assistant_prompt | llm.bind_tools(...)
```

### 这里用了哪些 LangChain 组件

1. `ChatPromptTemplate`  
   用于定义系统提示词和消息模板。

2. `llm.bind_tools(...)`  
   把工具集合绑定给大模型，让模型能够输出 `tool_call`。

3. `prompt | llm.bind_tools(...)`  
   通过 LCEL 管道操作把 prompt 和 llm 串起来，形成 runnable。

### 主 Agent 绑定的工具

```python
primary_assistant_tools = [
    tavily_tool,
    search_flights,
    lookup_policy,
]
```

以及几个“委托工具”：

- `ToFlightBookingAssistant`
- `ToBookCarRental`
- `ToHotelBookingAssistant`
- `ToBookExcursion`

### 重点理解

这里最值得学习的一点是：

主 Agent 绑定的不只是查询类工具，还绑定了几个 **Pydantic 结构化委托工具**。  
这些工具不是直接访问数据库，而是作为“切换到某个子 Agent”的信号。

也就是说：

**Agent 切换不是靠字符串判断，而是靠模型输出结构化的 tool_call。**

---

## 6. Agent 切换信号：Pydantic 工具模型

### 文件

`graph_chat/base_data_model.py`

这个文件中定义了两类非常关键的结构化模型。

### 6.1 主 Agent 用的“委托工具”

例如：

```python
class ToFlightBookingAssistant(BaseModel):
    request: str = Field(...)
```

这类模型的意义是：

- 让主 Agent 能结构化表达“我要把任务交给哪个子 Agent”
- 图层只需要判断 `tool_call.name`
- 不需要靠自然语言猜测下一步该切去哪里

这是一种很典型的 `tool-as-handoff` 设计。

---

### 6.2 子 Agent 用的“退出工具”

```python
class CompleteOrEscalate(BaseModel):
    cancel: bool = True
    reason: str
```

它的作用是：

- 当前任务已经完成
- 当前任务不适合本子 Agent 处理
- 需要把控制权交回主 Agent

因此它本质上是：

**子 Agent 回退主 Agent 的结构化信号。**

---

## 7. 子 Agent 的定义方式

### 文件

`graph_chat/agent_assistant.py`

这个文件定义了多个子 Agent，例如：

- 航班 Agent
- 酒店 Agent
- 租车 Agent
- 游览 Agent

每个子 Agent 的结构都基本一致：

1. 写一个领域专属的 `system prompt`
2. 定义 `safe_tools`
3. 定义 `sensitive_tools`
4. 用 `llm.bind_tools(领域工具 + [CompleteOrEscalate])`

### 例子：航班 Agent

```python
update_flight_safe_tools = [search_flights]
update_flight_sensitive_tools = [update_ticket_to_new_flight, cancel_ticket]

update_flight_runnable = flight_booking_prompt | llm.bind_tools(
    update_flight_tools + [CompleteOrEscalate]
)
```

### 重点理解

#### 1. 子 Agent 是领域化的

主 Agent 只负责识别意图和分发任务；  
真正的业务执行，是由子 Agent 完成的。

#### 2. safe / sensitive 工具分层

工具被分为：

- `safe_tools`：只读、低风险
- `sensitive_tools`：修改类、高风险

这为后面的 `interrupt_before` 中断机制做了准备。

#### 3. `CompleteOrEscalate` 是子 Agent 的退出机制

如果子 Agent 发现任务完成，或者当前问题不属于自己，就调用这个结构化工具，把控制权交回主 Agent。

## 8. 状态管理：LangGraph 的核心

### 文件

`graph_chat/state.py`

这个文件是整个项目最关键的状态设计。

### 状态结构

```python
class State(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]
    user_info: str
    dialog_state: Annotated[..., update_dialog_stack]
```

主要包含三个字段：

### 8.1 `messages`

用于保存完整的历史消息列表。

这里使用了：

```python
messages: Annotated[list[AnyMessage], add_messages]
```

表示 LangGraph 会自动帮你把每个节点新增的消息累积起来，而不是每次手动拼接全量历史。

这是一种 LangGraph 很常见的 reducer 设计。

---

### 8.2 `user_info`

保存用户信息，例如当前用户的航班信息。  
这样主 Agent 和子 Agent 都能共享统一的用户上下文。

---

### 8.3 `dialog_state`

这是整个项目中最值得学习的状态字段之一。

它不是单值，而是一个栈，并且更新方式由 `update_dialog_stack()` 控制：

```python
def update_dialog_stack(left: list[str], right: Optional[str]) -> list[str]:
    if right is None:
        return left
    if right == "pop":
        return left[:-1]
    return left + [right]
```

### 它的含义

- `None`：不改当前状态栈
- `"pop"`：弹出栈顶
- 其他字符串：压入一个新的子流程状态

### 它解决了什么问题

通过 `dialog_state`，项目可以知道：

- 当前在主 Agent 还是某个子 Agent 里
- 多轮对话时应该恢复到哪个子流程
- 子 Agent 退出后应该回到谁

你可以把它理解成：

**多 Agent 系统的“当前执行上下文栈”。**

---

## 9. 进入子 Agent：状态压栈与上下文切换

### 文件

`graph_chat/entry_node.py`

这个文件只有一个关键函数：

```python
def create_entry_node(assistant_name: str, new_dialog_state: str) -> Callable:
```

它会生成一个入口节点函数，在切入某个子 Agent 时执行。

### 核心逻辑

```python
return {
    "messages": [
        ToolMessage(...)
    ],
    "dialog_state": new_dialog_state,
}
```

### 它做了两件事

1. 追加一条 `ToolMessage`
2. 把 `dialog_state` 更新为新的子流程名

### 重点理解

这个入口节点不是业务处理节点，而是一个：

- 上下文切换节点
- 状态压栈节点
- 对子 Agent 的“正式接管”节点

所以主 Agent 切换到子 Agent，不是直接跳过去，而是先经过一个 `enter_xxx` 节点。

## 10. 子 Agent 内部工作流

### 文件

`graph_chat/build_child_graph.py`

这个文件负责定义四个子工作流，每个子工作流结构都很相似。

例如航班工作流大致包含：

- `enter_update_flight`
- `update_flight`
- `update_flight_safe_tools`
- `update_flight_sensitive_tools`
- `leave_skill`

### 最关键的部分：子工作流路由函数

例如：

```python
def route_update_flight(state: dict):
    route = tools_condition(state)
    if route == END:
        return END

    tool_calls = state["messages"][-1].tool_calls
    did_cancel = any(tc["name"] == CompleteOrEscalate.__name__ for tc in tool_calls)
    if did_cancel:
        return "leave_skill"

    safe_tool_names = [t.name for t in update_flight_safe_tools]
    if all(tc["name"] in safe_tool_names for tc in tool_calls):
        return "update_flight_safe_tools"

    return "update_flight_sensitive_tools"
```

### 这个逻辑的含义

1. 如果当前流程结束了，返回 `END`
2. 如果子 Agent 调用了 `CompleteOrEscalate`，跳转到 `leave_skill`
3. 如果调用的是只读工具，进入 `safe_tools`
4. 否则进入 `sensitive_tools`

### 这段代码的重要性

它体现了 LangGraph 中非常典型的模式：

- `LLM 决策`
- `Graph 路由`
- `Tool 执行`
- `再回到 LLM`

这就是一个完整的 Agent 闭环。

---

## 11. 子 Agent 退出：回到主 Agent

### 文件

`graph_chat/build_child_graph.py`

退出逻辑核心在 `leave_skill`：

```python
def pop_dialog_state(state: dict) -> dict:
    return {
        "dialog_state": "pop",
        "messages": messages,
    }
```

并且：

```python
builder.add_node("leave_skill", pop_dialog_state)
builder.add_edge("leave_skill", "primary_assistant")
```

### 这表示什么

- `CompleteOrEscalate` 只是发出“我要退出”的信号
- 真正退出子 Agent 的动作由 `leave_skill` 执行
- `leave_skill` 通过 `dialog_state = "pop"` 把当前子流程从状态栈中弹出
- 然后路由回主 Agent

所以这个项目里 Agent 切换的本质是：

- 进入子 Agent：`push`
- 退出子 Agent：`pop`

## 12. 顶层图：总路由与 Agent 切换

### 文件

`graph_chat/finally_graph.py`

这个文件是整个项目最核心的总装配文件。

### 12.1 固定入口：先获取用户信息

```python
builder.add_node('fetch_user_info', get_user_info)
builder.add_edge(START, 'fetch_user_info')
```

项目规定所有请求先经过 `fetch_user_info`，把用户信息写进 `state["user_info"]`。

这使得后续 Agent 都能共享统一上下文。

---

### 12.2 主 Agent 路由函数

```python
def route_primary_assistant(state: dict):
    route = tools_condition(state)
    if route == END:
        return END
    tool_calls = state["messages"][-1].tool_calls
    if tool_calls:
        if tool_calls[0]["name"] == ToFlightBookingAssistant.__name__:
            return "enter_update_flight"
        elif tool_calls[0]["name"] == ToBookCarRental.__name__:
            return "enter_book_car_rental"
        elif tool_calls[0]["name"] == ToHotelBookingAssistant.__name__:
            return "enter_book_hotel"
        elif tool_calls[0]["name"] == ToBookExcursion.__name__:
            return "enter_book_excursion"
        return "primary_assistant_tools"
```

### 它做了什么

1. 判断当前是否应该结束
2. 如果主 Agent 输出的是委托工具，就切到对应 `enter_xxx`
3. 如果输出的是普通主工具，就进入 `primary_assistant_tools`

### 重点理解

主 Agent 并不是自己做所有事情，而是：

- 自己能处理的问题自己处理
- 需要专门领域处理的问题，就委托给子 Agent

所以主 Agent 更像一个：

**总调度 Agent**

---

### 12.3 会话恢复：根据状态回到当前 Agent

```python
def route_to_workflow(state: dict) -> str:
    dialog_state = state.get("dialog_state")
    if not dialog_state:
        return "primary_assistant"
    return dialog_state[-1]
```

### 它的意义

每轮开始时，图都会根据 `dialog_state` 决定：

- 没有子流程状态时，进入主 Agent
- 如果状态栈里还有值，就恢复到当前子 Agent

### 为什么这很重要

因为这保证了多轮对话中：

- 系统不会丢失当前上下文
- 如果还在某个子任务里，就能继续在该子任务里对话
- 不用每轮都重新从主 Agent 开始判断

这就是“有状态对话”的关键实现。

## 13. 敏感操作中断与恢复

### 文件

`graph_chat/finally_graph.py`

图编译时用了：

```python
memory = MemorySaver()
graph = builder.compile(
    checkpointer=memory,
    interrupt_before=[
        "update_flight_sensitive_tools",
        "book_car_rental_sensitive_tools",
        "book_hotel_sensitive_tools",
        "book_excursion_sensitive_tools",
    ]
)
```

### 这表示什么

1. 使用 `MemorySaver()` 保存图执行过程中的状态
2. 在执行敏感工具之前中断流程
3. 等用户确认后，再从断点继续执行

### 这是一种典型的人机协同机制

例如：

- 查询类工具直接执行
- 修改订单、取消订单这类高风险动作先中断
- 等用户确认后再继续

这在真实业务中是非常重要的设计。

## 14. Tool 节点的执行方式

### 文件

`tools/tools_handler.py`

关键函数：

```python
def create_tool_node_with_fallback(tools: list) -> dict:
    return ToolNode(tools).with_fallbacks(
        [RunnableLambda(handle_tool_error)], exception_key="error"
    )
```

### 它的作用

- 使用 `ToolNode(tools)` 执行工具调用
- 如果工具执行出错，就用 fallback 生成错误反馈

### 为什么这很实用

如果没有这个处理：

- 工具异常时整个图可能直接中断

有了这个处理之后：

- 错误会被包装成 `ToolMessage`
- 继续回给模型，让模型有机会修正调用

这是一种很典型的工程稳健性设计。

## 15. API 如何调用图

### 文件

`api/graph_api/graph_views.py`

### 核心逻辑

```python
if question.strip().lower() != 'y':
    events = graph.stream({'messages': ('user', question)}, config, stream_mode='values')
else:
    events = graph.stream(None, config, stream_mode='values')
```

### 含义

- 普通用户输入：把用户消息塞给 graph 执行
- 如果输入是 `y`：表示批准中断后的敏感操作，从断点继续执行

然后通过：

```python
current_state = graph.get_state(config)
if current_state.next:
    result = "AI助手马上根据你要求，执行相关操作。您是否批准上述操作？输入'y'继续；否则，请说明您请求的更改。\n"
```

来判断当前是否停在中断点。

### 重点理解

这正是 LangGraph 的一个经典用法：

- `stream(...)` 跑图
- `interrupt_before` 做中断
- `get_state(config).next` 判断是否中断
- 再次调用 `stream(None, config, ...)` 从断点继续

## 18. 从 LangGraph 视角看，这个项目学什么

如果从 `LangGraph` 角度学习，这个项目最值得关注的点有：

### 18.1 `State` 设计

尤其是：

- `messages`
- `user_info`
- `dialog_state`

这三个字段如何支撑多轮对话与多 Agent 切换。

---

### 18.2 条件路由

项目大量使用：

- `add_conditional_edges(...)`
- `tools_condition(state)`

这说明 LangGraph 的核心不是“按顺序执行”，而是“根据状态动态路由”。

---

### 18.3 子 Agent 的 push/pop 栈管理

这个项目最值得你学习的一个设计就是：

- 进入子 Agent 时 `push`
- 退出子 Agent 时 `pop`

这种状态栈模式非常适合多 Agent 对话系统。

---

实现用户审批型工作流，这是 LangGraph 在业务落地里非常实用的一部分。

## 20. 一句话总结项目设计

这个项目的设计可以概括为：

- 用 `LangChain` 定义主 Agent 和子 Agent 的行为方式
- 用 `LangGraph` 定义多 Agent 之间的状态流转和工作流路由
- 用 `Tool Calling` 同时承担“业务工具调用”和“Agent 委托切换”两种职责
- 用 `dialog_state` 栈维护当前所处子流程
- 用 `interrupt_before + MemorySaver` 实现敏感操作的人机确认与恢复

如果后续要迁移到你的安防项目，这套思路可以直接复用到：

- 主 Agent：统一意图识别和任务分发
- 子 Agent：视频流 Agent、图片流 Agent、告警处置 Agent、知识问答 Agent
- 状态管理：记录当前处理的是哪类业务子流程
- 风控机制：对高风险操作做中断确认
